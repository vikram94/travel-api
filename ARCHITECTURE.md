# Architecture

A small, honest service: Java 21 + Spring Boot 4.1 on Spring JDBC over H2 in
PostgreSQL compatibility mode. No JPA, no Flyway, no external services. Two
concepts, one hard rule:

> A **transaction** is a live, editable charge. An **invoice** is a frozen
> snapshot of the transactions the moment they were billed. Later edits to a
> transaction never move a number on an invoice.

That single rule drives almost every decision below.

---

## 1. Overview and request flow

```
POST /transactions ──► validate ──► INSERT (unique external_id) ──► 201
                                        └─ duplicate ──► 409 existing_id

POST /invoices ──► shape/cap/dups (memory) ──► sort ids ──► SHA-256 fingerprint
        │                                                        │
        │                                            fast path: hash exists? ──► 409
        │                                                        │ miss
        └──────────► one TX ──► chunk ids by 500 ──► SELECT ... FOR UPDATE (asc)
                                 │                    load tax/fee lines (2 INs)
                                 │                    missing? 404 · mixed currency? 409
                                 ▼
                       items in request order · Math.addExact totals
                       rollups accumulated in sorted maps
                                 ▼
                       INSERT invoice · batch items + rollups (500)
                                 ▼
                       201 (header + rollups + first page, built in memory)
```

All validation, hashing and JSON serialization happen **before** the database
transaction where possible, so a bad request never takes a lock.

## 2. Data model

| Table | Purpose | Key constraints |
|---|---|---|
| `transactions` | live charges | `UNIQUE (external_id)` |
| `transaction_tax_lines` / `transaction_fee_lines` | named line items, ordered | PK `(transaction_id, position)`, `ON DELETE CASCADE` |
| `invoices` | frozen header + rollup totals | `UNIQUE (txn_set_hash)` |
| `invoice_items` | verbatim snapshot per included transaction | PK `(invoice_id, position)`, `UNIQUE (invoice_id, transaction_id)`, FK → `transactions` `ON DELETE RESTRICT` |
| `invoice_tax_rollup` / `invoice_fee_rollup` | pre-aggregated rollups | PK `(invoice_id, position)` |

- **Ids** are application-generated (`txn_<uuid v4>` / `inv_<uuid v4>`), so no
  surrogate keys are needed. If one is ever required it must be
  `BIGINT GENERATED BY DEFAULT AS IDENTITY` (never `AUTO_INCREMENT`) to stay
  Postgres-portable.
- **Money is `BIGINT` minor units** (scale 2, e.g. cents). IEEE floats are never
  stored. `total` is **gross** — tax and fee lines are descriptive and are never
  added on top.
- **Timestamps** are `TIMESTAMP(6)` and truncated to microseconds in the app, so
  what the cursor encodes is exactly what the database stores.
- **Indexes**: `idx_transactions_created (created_at, id)` and
  `idx_invoices_created (created_at, id)` serve keyset pagination;
  `idx_invoice_items_tx (transaction_id)` answers "is this transaction on an
  invoice?" for the PATCH/DELETE guard.

## 3. Transaction identity and concurrent POSTs

Uniqueness of `external_id` is a **database constraint**, not an in-memory check.
The insert runs inside a `TransactionTemplate`; a `DuplicateKeyException` is
caught **outside** that transaction and translated by a fresh read of the row
that won:

- The winner commits → 201 with its `id`.
- Every loser's insert trips the index → 409
  `{ "error": "duplicate_external_id", "existing_id": "<winner>" }`.

Comparison is case-sensitive and the value is stored exactly as sent (no trim,
no lowercase). This is why overlapping POSTs with the same `external_id` leave
exactly one row no matter how they interleave (test 6).

**Lock order** is fixed everywhere: **invoice first, then transactions in
ascending id order** (across chunks). Both invoice writers and transaction
PATCH/DELETE take `FOR UPDATE` on transaction rows, so invoices over the same
set serialize and no two paths can grab rows in opposite orders. H2 has no
`FOR SHARE`, so read-locking writers is not an option; `FOR UPDATE` on both
sides is the portable choice (Postgres `FOR SHARE` is a migration note only).

## 4. Taxes vs fees, and type-specific data

- **Taxes and fees are separate line tables**, never one polymorphic table: a
  tax may carry a nullable `rate` (`DECIMAL(7,4)`, scale-normalized for the
  rollup key), a fee never does. Both keep an explicit `position` so ordering
  is stable and reproducible.
- **`navan_fee` is a first-class transaction, not a `fee_line`.** It therefore
  never appears in `fee_rollup`; it is its own invoice item with its own total.
  Its `fee_kind` (`trip_fee` / `agent_call_fee`) is *derived* into a column on
  `transactions` so it is queryable without parsing JSON.
- **Type-specific data is hybrid JSON.** Anything the API merely echoes
  (flight coupons/OD/flight number, hotel name+address, rail legs) lives in a
  `TEXT` column holding the validated JSON, copied verbatim into the snapshot.
  Anything the service must *reason about* is either a real column
  (`fee_kind`) or a real table (tax/fee lines). This keeps the schema small
  without giving up queryability where it matters.

Validation is field-level and returns
`{ "error": "validation_error", "errors": [ { "field", "message" } ] }` with
paths like `metadata.coupons[0].arrival` or `tax_lines[0].rate`. `total` is not
verified against `fare + taxes + fees` — that is the client's business.

## 5. The invoice snapshot is not a live join

`invoice_items` stores a **copy** of each transaction's state at invoice time:
`external_id`, `type`, `currency`, `occurred_at`, `total_minor`, `fee_kind`,
plus `metadata_snapshot`, `tax_lines_snapshot` and `fee_lines_snapshot` as JSON.
`GET /invoices/{id}` reads **only** `invoices`, `invoice_items` and the rollup
tables — it never touches `transactions`. A later edit to the live row (even one
that bypasses the API) cannot change a served invoice (test 4).

The flip side is enforced in the other direction: a transaction that appears on
any invoice is protected by `ON DELETE RESTRICT` plus an application check, so
PATCH and DELETE return **409 `transaction_invoiced`** rather than silently
diverging from the frozen copy (tests 7, 8).

## 6. `txn_set_hash`: the fingerprint

A transaction set is identified by

```
txn_set_hash = SHA-256( join(sorted(ids), "\n") )   // 64 lowercase hex chars
```

- **Sorted** so `[a, b]` and `[b, a]` are one set (test 11: reversed order is 409).
- **Delimited with `\n`** so `["ab"]` and `["a","b"]` cannot collide.
- **`UNIQUE (txn_set_hash)`** on `invoices` is the actual guard: two concurrent
  identical creates race on the index, the loser catches `DuplicateKeyException`
  outside its transaction and returns 409 with the winner's id (test 12).
- A cheap **fast path** (`SELECT id FROM invoices WHERE txn_set_hash = ?`, no
  locks) rejects the obvious duplicate before any row is locked.
- The hash is **not** a payload hash: billed transactions are immutable, so the
  same set always means the same content. `DELETE /invoices/{id}` removes the
  row and frees the fingerprint, which is why the same set can be re-issued
  afterwards (test 11). Re-issue is a deliberate DELETE-then-POST, never a
  silent overwrite.

Consequence: a transaction may legitimately appear on several invoices as long
as the **sets differ** (e.g. `[a]` and `[a, b]`); what is impossible is two live
invoices over the identical set.

## 7. Rollups are stored, not computed on read

At create and PATCH the service accumulates `tax_rollup` / `fee_rollup` in
sorted maps (tax keyed by name **and** scale-4-normalized rate, fee by name) and
writes them to `invoice_tax_rollup` / `invoice_fee_rollup` in one batch. Every
`GET /invoices/{id}` returns the **full** rollups from those tables, while items
are paged.

Why: `GET` cost then depends on the number of rollup lines, **not** on the
number of items. A 1000-item invoice answers `GET` in the same time as a 5-item
one, and pages of items never have to re-aggregate. PATCH rebuilds are
delete-and-reinsert, so rollups can never drift from the item set.

## 8. Chunked `FOR UPDATE` load and the 1000-per-request guardrail

Creating an invoice over many ids must not issue one giant `IN (...)` and must
not lock rows in an unstable order:

1. Ids are validated in memory, deduplicated-reported (409
   `duplicate_transaction_id`) and capped. Over the cap → 400
   `{ "error": "too_many_transactions", "max": 1000 }`.
2. The sorted id list is **chunked by 500**. Each chunk is loaded with
   `SELECT ... WHERE id IN (:chunk) ORDER BY id FOR UPDATE`, and tax/fee lines
   with two `IN`s ordered by `(transaction_id, position)`. Because the ids are
   sorted, the global lock order is ascending id across all chunks.
3. Missing ids are collected across chunks and reported together as 404
   `{ "error": "transaction_not_found", "ids": [...all missing...] }`. Mixed
   currency fails fast **while loading** with 409 `mixed_currency`.
4. Items keep the **request order**; totals are summed with `Math.addExact` on
   minor units; metadata is copied verbatim; lines are serialized to JSON.
5. The invoice row is inserted, then items and rollups are `batchUpdate`d in
   batches of 500, then the transaction commits.

`invoice.max-transactions=1000` is a **per-request guardrail**, not a claim that
invoices cannot be larger. It bounds how much work one HTTP request may ask for
(and therefore how long it can hold locks). Handling 1000 gracefully —
chunked loads, batched inserts, stored rollups, paged items — is the real
requirement; the cap just stops a request from being unboundedly expensive.

## 9. Pagination is keyset, never offset

Both lists and invoice items use a seek on a stable ordered key:

| List | Order | Cursor |
|---|---|---|
| `GET /transactions` | `(created_at, id)` | base64url `<created_at ISO micros>\|<id>` |
| `GET /invoices` | `(created_at, id)` | same format, headers only |
| invoice items | `position` | the last `position` seen |

- SQL is `WHERE (created_at, id) > (:c, :id) ORDER BY created_at, id LIMIT :n+1`
  (items: `WHERE invoice_id = ? AND position > ? ORDER BY position LIMIT ?+1`).
  One extra row is fetched to decide whether a `next_cursor` exists.
- **No `OFFSET`.** Offset pagination degrades linearly on high-traffic tables
  and can duplicate or skip rows when inserts land between pages. Keyset pages
  stay stable: rows inserted between two page reads may appear on a later page,
  but no *existing* row is ever duplicated or skipped (test 17).
- Limits: transaction/invoice list default 50, max 100; invoice items default
  100, max 500. Out-of-range or unparseable limits are **400**; a malformed
  cursor is **400 `invalid_cursor`**; `next_cursor` is `null` on the last page.
- Child lines for a page of transactions are fetched with **one `IN` per line
  table**, not per row.

## 10. Failure modes, operations, and what we would do next

**503, never 500, for contention.** Lock waits, deadlocks, serialization
failures and query timeouts are transient: the API maps them to **503** with
`Retry-After: 1` and `{ "error": "busy" }`. This covers Spring's
`ConcurrencyFailureException` (incl. `CannotAcquireLockException` /
`DeadlockLoserDataAccessException`) and `QueryTimeoutException`, plus a
SQLState/error-code walk (H2 `50200`/`50100`, SQLState `40001`, `55P03`,
`HYT00`/`HYT01`) as a backstop. Writes run with a ~10 s query timeout and H2
`LOCK_TIMEOUT=5000`, so a stuck writer fails fast and retryably instead of
hanging. A held row lock therefore produces a clean 503 the client can retry
(test 19) — the row is left untouched.

**H2 file vs Postgres.** The service is **stateless**; all durability and
uniqueness live in the database. H2 in PostgreSQL mode is a single-process
choice: it makes the project runnable with zero setup (`jdbc:h2:file:./data/travel`)
and keeps SQL portable. In production the same code points at Postgres, where
`FOR SHARE` on writers and real connection pooling across instances become
available. Nothing in the schema or SQL is H2-specific beyond the compatibility
mode.

**What fails first under high volume.** Writes serialize on the row locks they
take (transaction PATCH/DELETE and invoice create over the same transactions),
and on the two unique indexes (`external_id`, `txn_set_hash`) — these are the
correct global arbitration points. Reads are cheap and page-independent
(stored rollups, keyset seeks). So under load the first symptoms are lock waits
turned into 503s, not corrupted data or unbounded scans.

**Honest next steps, in order of value.** (1) The 1000 cap is the honest
boundary of a single-request build; the natural next step is to **split** a
large invoice into explicit segments or move snapshot construction to an
**async** job the client polls — both keep the frozen-snapshot guarantee while
removing the per-request ceiling. (2) Add a `GET /health/ready` that checks the
database rather than a static OK. (3) Move the "is it invoiced?" guard fully
into the database with a `NOT NULL` sentinel or a trigger instead of an
application check. (4) Add metrics for 503 rate and lock-wait latency so
contention is visible before it becomes a page.
